# Menu du Jour

A lightweight macOS menu bar utility that simulates a right-click at the text caret position when a keyboard shortcut is pressed (like the Windows "menu key").

> `AGENTS.md` is a symlink to this file — edit only `CLAUDE.md`.
> If `CLAUDE.local.md` exists, read it too: it holds the owner's machine and planning rules and is not in git.

## Project Structure

```
MenuDuJour/
├── Package.swift                      # SwiftPM config, macOS 13+; 3 targets: app, core library, tests
├── Sources/
│   ├── MacMenu/                       # executable target "Menu du Jour" — all system-framework I/O lives here
│   │   ├── MacMenuApp.swift           # @main entry point, MenuBarExtra UI, AppDelegate wiring, LaunchAtLoginManager, hotkey dispatch
│   │   ├── AccessibilityHelper.swift  # Finds caret/selected-item position via macOS Accessibility (AX) APIs

│       ├── CaretRange.swift           # ordered AX range/text-marker plans and logical boundary mapping
│       ├── AppBehaviorPolicy.swift    # built-in app compatibility rules (native Office Shift+F3; where keycode 110 is unsafe; Shift+F10 for Office web editors)

│       ├── AXActivationPolicy.swift   # which AX-nudge failures are permanent (settled) vs worth retrying
```

## Build & Run

```bash
swift build    # compile
swift test     # run unit tests (MenuDuJourCore only — the AX/CGEvent layer is untestable by design)
swift run      # launch (appears in menu bar)
```

Testing policy: pure logic goes in `MenuDuJourCore` with tests (TDD); system-framework glue stays in `Sources/MacMenu` and is validated via Diagnostic Mode + manual runs. One exception has its own check: the case-cycle JavaScript is pure logic that `swift test` cannot reach, so `node macmenu_scripts/check-browser-tokenizer.js` extracts the literal from the Swift source and runs it against the same cases the Core tests pin.

## Debugging a live build

- **"Nothing works anywhere"** (⌥M dead in every app, ⇧F3 passes straight through) means the event tap is not installed — almost always a lost Accessibility grant. An ad-hoc build gets a new signature every time, `build-release.sh` resets the grant on purpose, and the app then polls for permission every 2s. The first log lines say which state it is in: `ShortcutManager: Accessibility NOT granted — hotkeys are inactive…` versus `…event tap installed — menu ⌥/, change case ⇧F3, synthetic-input fallback on` (it also logs a failed tap creation, system disable/re-enable of the tap, wake re-enables, each hotkey press with the app it went to, and deliberate change-case pass-throughs). Re-grant in System Settings → Privacy & Security → Accessibility (toggle off/on, or remove and re-add). A Developer ID–signed build keeps its grant across rebuilds, because TCC then matches the signing identity instead of the binary's hash.
- **Reading the app's own logs.** Every diagnostic goes through `NSLog("%@", "[Menu du Jour] …")` — the `%@` keeps user text out of the format string. Two consequences, both of which cost a day on 2026-09-27:
  - the text is in the log's *composedMessage*; the *eventMessage* is just `%@`. Filter by process (`log stream --predicate 'process == "Menu du Jour"'`, which `build-release.sh --log` now does), never by `eventMessage`;
  - unified logging **redacts** `%@` arguments, so even a correct filter shows our lines as `(Foundation) <private>`. To read them, run the binary from a terminal, where `NSLog` also writes to stderr unredacted:
    ```bash
    pkill -x "Menu du Jour"
    ".build/Menu du Jour.app/Contents/MacOS/Menu du Jour" 2>&1 | tee /tmp/mdj.log
    ```
    It keeps the bundle's identity (same defaults domain, same Accessibility grant as the `open`-launched app).
- **Beeps come from one place**: `CaseToggler.fail` → `NSSound.beep()`. In a system log without our text, a `systemsoundserverd … actionID 4096, inClientPID <ours>` line is that beep.

## Key Details

- **Default shortcut**: ⌥M (Option+M)
- **Change-case shortcut**: ⇧F3 (Shift+F3, configurable) — cycles the word under the caret (or the selection) lower → Title → UPPER, Word-style. On media-key keyboards F3 needs `fn` unless "Use F1, F2… as standard function keys" is on. Persisted as `caseShortcutKeyCode`/`caseShortcutModifiers`.
- **Case-shortcut pass-through** has three distinct rules, and conflating the first two was a bug: (1) Native-Shift+F3 Office apps (Word, Excel, PowerPoint, OneNote) claim **Shift+F3 specifically**, so they only get a pass when the configured hotkey *is* Shift+F3 — passing a rebound ⌃⌥C through to Word would silently disable the feature there for nothing. (2) Apps in the user's `caseShortcutPassThrough` array (default `com.microsoft.VSCode`) claim **whatever is bound**, because the point is that we cannot serve them at all. (3) **Outlook is a special case and is deliberately NOT in the native-Shift+F3 group**: Outlook for Mac is web-backed and binds no Shift+F3 of its own (verified 2026-09-04 — ⇧F3 does nothing there even with this app quit), so deferring to it gave the user *nothing*. Its compose body also defeats every AX write path, so the only thing that can serve it is the opt-in clipboard fallback. The rule is therefore gated on that fallback: while it is **off**, pass the key through (a silent no-op, not a beep, whatever the binding); once it is **on**, claim the key so the case cascade reaches the clipboard fallback. All three decisions live in `AppBehaviorPolicy.shouldPassThroughCaseShortcut`. Add custom entries with: `defaults write com.luca.menudujour caseShortcutPassThrough -array com.microsoft.VSCode`
- **Case-cycle strategy order**: supported browsers first run in-page JavaScript via Apple Events (rich formatting and undo survive), then the verified AX cascade, then — only if enabled — the clipboard fallback. A successful AX write return code is NOT proof the edit happened (WebKit and Chromium report success while editing nothing; Outlook can half-apply writes), so every AX path is verified by read-back and the cascade aborts on unexpected text. The range-replace write (`AXReplaceRangeWithText`) is confined to native views, like the selected-text write: in web content it does not merely lie (Safari answers YES editing nothing, Chromium answers NO) — Outlook's compose body actively **corrupts**, inserting a paragraph break that splits the target word (measured 2026-09-27), and the read-back catches the divergence only *after* the damage, aborting before the clipboard fallback is ever reached. So web content skips both range-targeted AX writes and goes whole-value (path C, uniform formatting only) → clipboard fallback. The browser JS path only runs when the AX focused element is actually web content — otherwise ⇧F3 in the address bar would edit the page — and it handles `<input>`/`<textarea>` via `selectionStart`/`selectionEnd`, because `window.getSelection()` does not report selections inside form fields. It also descends into same-origin iframes (Outlook web, CKEditor, TinyMCE). "Nothing to transform" from the page falls through to AX rather than ending the attempt.
- **Clipboard fallback (opt-in, off by default)**: toggle **"Change Case: synthetic input fallback"** in the menu-bar dropdown, or `defaults write com.luca.menudujour enableClipboardCaseFallback -bool YES`. Both write the `enableClipboardCaseFallback` UserDefault; `ClipboardCaseFallback.isEnabled` is its single get/set accessor, and a change posts `UserDefaults.didChangeNotification`, which `ShortcutManager` observes to re-publish the flag into the tap snapshot — so the Outlook pass-through gate (rule 3 above) updates live, no restart needed. When every AX path declines, `ClipboardCaseFallback` first tries **typing** the replacement: key events carrying the text as a Unicode string (`CGEventKeyboardSetUnicodeString`), posted to the originating PID only, flags cleared (the hotkey's ⇧ is still held). It runs only when AX gave us the planned edit, the selection is confirmed equal to the target (this excludes terminals, where typing would insert rather than replace), and the input source is a plain keyboard layout (an input method would capture the keys). It needs no clipboard at all — verified in Outlook's compose body 2026-09-27, clipboard byte-identical. Once events are posted the press ends there whatever the read-back says: they cannot be recalled, and a late delivery plus a paste would be two edits (Ledger L3). Styled runs inside a word are flattened to the style at the selection — accepted by the owner. Otherwise `ClipboardCaseFallback` copies the selection with ⌘C, transforms the RTF flavour as an `NSAttributedString` per attribute run (`AttributedCaseCycle` — formatting survives, unlike a whole-value write), pastes it, and restores the original clipboard including every flavour. It is the only path that drives the target app with synthetic keystrokes, which is why it is opt-in; it is also the only path that works in Outlook's compose editor and terminals. Four preconditions, each closing a way it could act on something that is not a text edit (REVIEW.md 2026-07-27 F3/F5/F7): the focused element must be a **text-editing context** (a text role or one advertising a text selection — without this, ⇧F3 in a Finder file list reached the ⌘C); the copied payload must pass `ClipboardPayloadPolicy`, which rejects file URLs, images and other objects *whatever text they also carry* (a copied file advertises its filename as plain text); the originating PID is rechecked immediately before both ⌘C and ⌘V; and runs are serialized, with the clipboard restored only if it still holds what we put there, so overlapping presses cannot restore our temporary value over the user's and a genuine Copy in the window is left alone. That ownership check, and putting the selection back when no paste happens, apply on **every** exit — both are `defer` obligations taken where the state is disturbed, because when they were steps on the success path each failure exit leaked one of them (REVIEW.md 2026-07-28 F1/F5, Ledger L4). The transformed text goes back in the flavour it was read in: RTFD in, RTFD out, so an inline image survives (Ledger L5).
- **Requires Accessibility permission** — app prompts on first launch
- **Start at Login** — toggle in menu dropdown, uses `SMAppService.mainApp` (ServiceManagement framework)
- **No external dependencies** — uses only system frameworks (SwiftUI, Carbon, ApplicationServices, ServiceManagement)
- **Hotkey persistence** — saved in UserDefaults (`shortcutKeyCode`, `shortcutModifiers`) as Carbon key codes/modifiers
- **CGEvent tap** — intercepts key events at session level (`headInsertEventTap`), takes priority over other apps (e.g. BetterTouchTool). **The tap runs on its own thread** (`com.luca.menudujour.event-tap`) with its own `CFRunLoop`. This is not optional: an active tap holds every keystroke on the machine until this process replies, and the reply happens on the run loop the tap source is attached to. While the tap lived on the main run loop, any slow main-thread work — the verified AX cascade, an Apple Event, a TCC consent prompt — froze typing system-wide and got the tap killed by timeout. Dispatching handlers off the callback did not help, because they were dispatched back onto that same run loop. Handlers still run on main (AppKit, AX, NSAppleScript); if they block, only this app's UI suffers. Everything the callback reads therefore crosses a thread boundary and lives in the lock-protected `TapState` snapshot — never read `@Published` state, UserDefaults or NSWorkspace from the callback
- **Apple Events are never sent from a thread that matters** — `AppleScriptRunner` owns the one thread all `NSAppleScript` runs on, and callers wait with a deadline (2s for the browser JS, its only remaining caller). Permission is checked with `AEDeterminePermissionToAutomateTarget(…, askUserIfNeeded: false)` first, because the *first* Apple Event to an app opens the Automation consent dialog and does not return until the user answers it; an undetermined grant kicks the prompt off in the background and gives up on that press
- **Never post synthetic events blindly** — every synthetic keystroke/click needs its precondition positively verified via AX first (e.g. arrow-down only when a menu is open with no item focused); "probably harmless" global events mutate state in whatever app is frontmost (review verdict, REVIEW.md 2026-07-10 F4)
- **Every operation belongs to the app the key was pressed in** — the tap records `kCGEventTargetUnixProcessID` (captured atomically with the event; verified to carry a real target PID at our head-inserted session tap) and hands it to the handler. `OriginatingApp.stillFrontmost` must gate every AX query and every synthetic event, because an operation spans up to ~1s of polling and the user can switch apps inside it. This was only ever implicitly safe while the tap shared the main run loop; it is now explicit (REVIEW.md Ledger L1). The case-shortcut pass-through cannot be deferred, so it resolves the event's target PID through a PID→bundle-ID map instead of "who is frontmost" — the mapping never goes stale, whereas frontmost-ness is published from a main-queue observer and is wrong exactly when main is blocked
- **"Changed" is not "changed to what we asked for"** — pasteboard `changeCount` advancing proves Copy produced *something*, not that text was selected; an AX value differing from before does not prove it holds the replacement. Compare against the expected value or report the result unverified (Ledger L2)
- **Undoing borrowed state is an obligation, not an exit step** — when a path moves the user's selection or borrows their clipboard, take the restore where the state is disturbed (a `defer`, a scope guard) rather than calling it at each return. Cleanup wired only into the success path leaks on every failure exit; that produced two separate findings in one session (Ledger L4). Two things must *not* be restored: a verified edit (it restores its own caret) and a diverged write (the offsets no longer describe the text — see the abort rule above)
- **Round-trip content in the flavour it arrived in** — read the richest representation and write that same one back. RTF cannot carry an attachment, so re-encoding an RTFD selection as RTF deletes the inline image, and a paste over the original selection makes that permanent. If the payload cannot be re-encoded faithfully, decline the operation instead of flattening it (Ledger L5)
- **One definition of "word"** — `MenuDuJourCore.CaseCycle` owns it: letters/digits, with an apostrophe joining two *letters* ("dell'acqua" is one word, "boys'" is not). Any tokenizer outside Core must match it, or ⇧F3 behaves differently depending on which path serves the press. The in-page JS is the only one; `macmenu_scripts/check-browser-tokenizer.js` extracts that literal from the Swift source and runs it against the Core tests' cases, because `swift test` cannot reach it (Ledger L6)
- **A deadline bounds our waiting, not the operation** — a timed-out Apple Event keeps running. For a *mutating* script that makes the outcome indeterminate, not failed: nothing further may be attempted on that press, or two edits compose. Read-only queries may degrade normally (Ledger L3)
- **AX messaging timeout** — capped at 0.5s process-wide (set on the cached system-wide element in `AccessibilityHelper`) so a hung app can't block us
- **Caret detection**: tries legacy AX character bounds first, then web-style AX text markers. Chromium/Electron controls can return the entire field for every derived marker range; those false positives are rejected. For a readable, writable non-empty selection, the last resort briefly collapses the range to the last character's two boundaries, reads the app-created collapsed marker positions, restores the original range, and verifies both range and selected text before any click. Query-plan and logical-boundary mapping live in `MenuDuJourCore/CaretRange.swift`.
- **No better caret source exists for a third-party app.** Cotypist (system-wide AI autocomplete, `app.cotypist.Cotypist`) was inspected on 2026-09-27 (`nm -u`, bundle layout): it is not an input method; it tracks the focused field with `AXObserver` notifications (`AXFocusedUIElementChanged`, `AXSelectedTextChanged`, `AXValueChanged`), reads caret geometry through the same AX range and text-marker queries we use, and inserts text by posting key events carrying a Unicode string (`CGEventKeyboardSetUnicodeString` + `CGEventPostToPid`) — the technique our typing fallback copies. The only exact caret channel is the one input methods get (see the fn-key limitation below).
- **PowerPoint** is served entirely by the contextual-menu key. It keeps AX focus on an `AXScrollArea` while slide text is being edited, so if that key ever fails there, every caret strategy resolves to the slide and the imprecise fallback opens the *slide* menu — the wrong menu. `caretPosition` therefore declines outright for PowerPoint rather than guessing. This replaced ~300 lines (`PowerPointCaretLocator`, `SlideCoordinateMapper`) that asked PowerPoint for its caret over Apple Events and mapped slide coordinates to the screen, plus the per-target Automation grant and consent alert they needed — all of it scaffolding for computing a pixel that the app now places itself.
- **Coordinate spaces**: AX positions and CGEvent posts are global CG coordinates (top-left origin). Never compare against `NSScreen.frame` (bottom-left Cocoa) — use `CGDisplayBounds`
- **Finder support**: detects selected rows/children in list/table/outline views for accurate right-click positioning
- **AX activation (`prewarmAccessibility`)**: browsers and Electron apps keep their accessibility trees switched off until an assistive client asks, and each family wants a different nudge. All three run on app activation, not at hotkey time, because every one of them rebuilds the tree asynchronously. PID caches are pruned on `didTerminateApplicationNotification` — PIDs get recycled, and a cache that never forgets would skip a new process that inherited a dead one's PID.
  - **Electron** (Slack, Discord, Notion, Obsidian, Teams, VS Code…): `AXManualAccessibility`, which Electron added specifically for non-VoiceOver assistive tech and which has no window-management side effect. Attempted on *every* app that activates — the only way to catch Electron apps we've never heard of. The PID cache key is **settled, not succeeded** (`AXActivationPolicy`): a native app's `attributeUnsupported` is permanent and must be cached too, or every activation *and* every hotkey press re-sends the write and can spend the 0.5s AX timeout on it. Transient failures (`cannotComplete` from an app still launching) still retry — that is the REVIEW.md 2026-07-10 F6 guarantee.
  - **Firefox**: no attribute to set. Mozilla resolved this by enabling the engine when the application element's role is read (bug 1664992 comment 7 / bug 1845364), so the nudge is a plain `kAXRole` read.
  - **Chromium**: `AXEnhancedUserInterface`. Note the cost — it is VoiceOver's attribute, so Chromium treats it as "a screen reader is present", and it is a known cause of sluggish window positioning for Rectangle/Magnet/Moom against that browser. Worth it by default (without it the caret is invisible to us in every Chromium browser), but escapable: `defaults write com.luca.menudujour disableChromiumEnhancedUI -bool YES`
- **Chromium AX writes are asynchronous**, so verified caret-boundary probes poll their read-back before continuing. Its imprecise fallback is the same as every app's — Shift+F10 was retired (2026-07-14 diagnostics: it opened a menu in NONE of the fallback contexts, while `kAXShowMenuAction` and a center right-click each worked in all of them)
- **Menu detection**: open context menus are INVISIBLE in the AX tree (verified 2026-07-13 in TextEdit, Chrome, Outlook — no AXMenu child, focused element unchanged); detect them as on-screen windows at the pop-up-menu window layer via CGWindowList (`MenuDetection.swift`, no extra permission needed for layer/owner-PID)
- **Diagnostic Mode** (menu toggle): hotkey runs `AXDiagnostics.run()` against the focused app — reports focused-element roles, advertised AX actions (incl. `kAXShowMenuAction` + its AXError), caret bounds resolution, and which strategies actually open a menu. Report goes to log + clipboard. Used to decide per-app strategy changes with data
- **The contextual-menu key (virtual keycode 110) is the FIRST strategy** — `ContextMenuKey`, posted with `postToPid` to the app the hotkey was pressed in. AppKit routes it through `NSApplication._handleContextMenuHotKey:` → `showContextMenuForSelection:`, so the *app* places the menu from its own caret and selection state. That is what Windows' menu key does, and it is strictly better than any coordinate computed from outside. All the caret machinery below is now the **fallback** for apps that ignore it.
  - Measured 2026-07-28 (post the key, watch for a pop-up-layer window): menu opened in TextEdit, Word, Outlook (native surfaces only — see the compose-body exception below), Excel, Finder and Mail; **not** in Chrome, Codex/ChatGPT, or Android Studio (focused role `JavaAxIgnore`). The split is AppKit vs any toolkit that draws its own UI — Chromium and Java/Swing both handle their own key events and never reach AppKit's hotkey path. This fixed all three known-broken cases at once: PowerPoint beeped, Finder and Word placed the menu nowhere near the caret.
  - **No allowlist and no OS version check**, deliberately: the result is verified at runtime against `MenuDetection`, so an app (or OS) that does not implement it produces no menu and falls through automatically. Nothing to maintain — *provided the key is inert where it fails*, which is the assumption the Outlook exception below broke.
  - Safe to post, unlike ⌃↩ — which was the earlier candidate and which apps bind to Send / Run Cell / other irreversible actions. Keycode 110 is a dedicated menu key nothing else binds, and it types nothing: the three measured apps that expose text to AX were byte-identical afterwards. `postToPid` means it reaches only the originating app and no other event tap sees it.
  - **"Types nothing" is not "changes nothing" — check the selection, not just the text** (2026-08-06). Outlook's web-backed compose body answers keycode 110 by selecting the word ONE LINE BELOW the caret and opening its menu around that word: measured, a caret at index 15 on line 0 became a selection of `"ads"` at 34..36, the last word of line 1, walking down another line on each further press. Outlook's *text* is byte-identical throughout, which is why the 2026-07-28 measurement — which compared text — passed it. Nothing we send corrects Outlook's hit test, and the damage lands before any runtime check can see it, so `AppBehaviorPolicy.shouldPostContextMenuKey` blocks the key there and the press goes straight to the caret path (Outlook's AX caret geometry is accurate on every line — verified over 30 caret positions).
  - The exclusion is keyed on **app + web content**, because neither alone is right: Outlook's own native surfaces (message list, subject field) are where the key works, and Mail's compose editor is WebKit too yet behaves correctly. Web content is identified by `AccessibilityHelper.isWebContent` (the `AXDOMIdentifier` attribute) — one definition, shared with the case-cycle cascade.
  - **Outlook's compose body gets a LEFT click at the caret, not a right-click** (owner report 2026-10-22): Outlook for Mac shows its spelling suggestions on a left click on the word there. `AppBehaviorPolicy.caretClickButton` (Outlook + web content, the same scoping as the key exclusion); only the precise `.caret` result gets it — an imprecise centre-of-element left click would move the caret. The point is nudged 1pt left so the hit test lands inside the word before the caret, not past its end. Owner-verified 2026-10-23.
  - **Outlook's menu can take ~400ms to appear**, past the 300ms `menuDeadline`, so a press that *is* served by the key can still be declared a failure and get a second menu from the fallback click. Not yet addressed; this is the first thing to check if a menu ever flickers in an app the key normally serves.
  - **"A menu appeared" includes in-page menus.** A web app's own (ARIA) menu is not a window, so `MenuDetection.popUpMenuWindowExists` cannot see it; it shows instead as keyboard focus on an `AXMenuItem` inside an `AXMenu`. `ContextMenuKey.attempt` counts either. NSMenus never take AX focus, so the two cannot be confused. Before this, a web app's own menu counted as "no menu" and the fallback click landed on top of it.
  - **Office for the web gets Shift+F10, not keycode 110, and never the fallback click** (verified 2026-09-28 in Firefox: PowerPoint and Excel on SharePoint). Office's web editors draw their own caret and context menu; the caret the page reports is a fixed point off the slide (AX focus on an `AXList`, the same `(397, 324)` on every press), so the click opened the browser's menu in the wrong place without Office's spelling suggestions. Shift+F10 makes Office open its own menu at its own caret, identical to a real right-click. The editor is recognised by the host of the web page *nearest* the focused element — it is always a frame on `*.officeapps.live.com`, even when the address bar shows `*.sharepoint.com` — via `AccessibilityHelper.nearestWebPageHost` and `AppBehaviorPolicy.menuRequest(forWebPageHost:)`. If no menu is confirmed within 0.6s the press beeps and does not click (`mayClickAfterFailedMenuRequest`): the wrong menu is worse than none, the judgement already made for native PowerPoint. Every browser press logs the page host, so an Office domain we do not match shows up in one log run. Known gap: Excel's **formula bar** ignores Shift+F10 (beep, no menu).
  - `showContextMenuForSelection:` itself is unreachable from another process — it is an in-process AppKit responder action, and post-SIP macOS blocks cross-process code execution into signed apps. The keystroke is the only handle on that path; `kAXShowMenuAction` is a *different* code path (`accessibilityPerformShowMenu`, positioned via `accessibilityWindowPointForShowMenu`), which is element-centred and is why it misplaced the menu in Finder and Word.
- **Flow**: Hotkey press → tap callback captures the target PID → async dispatch to main → if the focused web page is an Office editor (`*.officeapps.live.com`), post Shift+F10 and stop (menu or beep, never a click) → otherwise `AppBehaviorPolicy.shouldPostContextMenuKey` (skips the key in Outlook web content) → `ContextMenuKey.attempt` posts keycode 110 to that PID and watches for a menu. If one appears, done — nothing below runs. Otherwise (Chromium, Electron, Java/Swing, Outlook's compose body) → `AccessibilityHelper.caretPosition()` → legacy range / text marker / verified selection-boundary → `RightClickSimulator.rightClick(at:)` — or, on the imprecise fallback: `kAXShowMenuAction` (element + ancestors, confirmed against `MenuDetection`), then a right-click at the focused element's center

## Distribution

The app is distributed directly (notarized, outside the Mac App Store) since it uses CGEvent taps and Accessibility APIs incompatible with App Store sandboxing.

### Build .app bundle

```bash
# Unsigned (local testing) — stops any running instance first, ad-hoc signs,
# resets the Accessibility TCC grant (ad-hoc signatures change every build)
bash macmenu_scripts/build-release.sh

# Signed with hardened runtime (for distribution; keeps its TCC grant)
bash macmenu_scripts/build-release.sh "Developer ID Application: Luca Coppadoro (UF53RV3BF3)" --install
```

### Notarize & staple

```bash
# Credentials live in the login keychain as profile "menudujour-notary"
# (created with `xcrun notarytool store-credentials`; keychains are per
# machine, so each Mac that notarizes needs its own). Team ID UF53RV3BF3.
xcrun notarytool submit ".build/Menu du Jour.zip" \
  --keychain-profile "menudujour-notary" --wait

xcrun stapler staple ".build/Menu du Jour.app"

# Re-zip for distribution
ditto -c -k --keepParent ".build/Menu du Jour.app" ".build/Menu du Jour.zip"
```

- `macmenu_scripts/check-browser-tokenizer.js` — development check (needs `node`, not part of the build): runs the embedded case-cycle JS against the Core tokenizer's cases

## Known Limitations

- **Firefox** (verified 2026-09-28): ordinary pages are served by the contextual-menu key — Firefox opens its own menu at the caret, spelling suggestions included — so the AX caret path is only the fallback there. Office's web editors in Firefox use Shift+F10 (see the contextual-menu key section).
- **Browsers (general)**: CGEvent right-clicks trigger the browser's native context menu, not web app JavaScript context menus (e.g. Outlook web). Office's web editors are the exception we handle, by asking with Shift+F10 instead of clicking
- **The fn/globe key's emoji picker cannot be imitated** (spike 2026-09-28). The picker lands exactly on the caret in every app because it *is* an input method (`com.apple.CharacterPaletteIM`, `InputMethodType = palette`): selecting it with `TISSelectInputSource` makes the focused app open an input-method connection to it, and it then asks the app's own text view for the caret rect. We built a throwaway palette-type input method to do the same for the context menu. macOS registers it correctly (`TISCategoryPaletteInputSource`) but refuses to enable it from software — `TISEnableInputSource` returns noErr and changes nothing, and `TISSelectInputSource` returns -50 — whether ad-hoc signed, Developer ID signed, or **notarized and Gatekeeper-accepted**. The same call does enable Apple's own disabled palette (`com.apple.50onPaletteIM`), and a third-party *keyboard* input method is refused the same way, so third-party input methods need user approval, and palettes have no approval UI. Owner-level enabling fails too: adding the same `AppleEnabledInputSources` entry System Settings writes for Apple's picker (`Bundle ID` + `"Non Keyboard Input Method"`) to `com.apple.HIToolbox`, then logging out and in, leaves it disabled and unselectable — the input-source server ignores non-Apple palettes regardless of who asks. Untested only: a system-wide install in `/Library/Input Methods` (needs sudo; judged very unlikely to differ). The owner rejected the ordinary-input-method alternative (it would have to stay selected as the keyboard). Do not retry without a new macOS mechanism.
- **Mouse cursor**: simulating a right-click unhides the cursor in apps that hide it while typing (macOS behavior, unavoidable)
- **Change case (⇧F3)**: in browsers, full support (incl. rich text) requires the one-time "Allow JavaScript from Apple Events" toggle; without it, web editors fall back to AX and work only on uniformly-formatted content — mixed formatting beeps rather than risk flattening it. Outlook's compose editor cannot be served by AX at all when a signature or any styling is present: its edit paths lie about success — worse, `AXReplaceRangeWithText` there actively **corrupts**, inserting a paragraph break that splits the target word (measured 2026-09-27), and `kAXSelectedText` can delete without inserting. Both range-targeted AX writes are therefore skipped in web content, so the cascade reaches the clipboard fallback instead of aborting on the damage it just caused. Outlook, terminals, and Electron apps with no readable AX text are exactly what the opt-in clipboard fallback is for. With it off: terminals and Electron beep, while **Outlook** (which binds no native Shift+F3 to defer to) passes the key straight through as a silent no-op — see the pass-through rule above. Undo granularity of the replacement depends on the target app
- **Some apps position the menu wrong or not at all** — under investigation via Diagnostic Mode. The imprecise fallback leads with `kAXShowMenuAction` (element + ancestors) and now confirms a menu actually appeared before skipping the click, since several apps accept the action and show nothing. Residual risk: if `MenuDetection` ever produces a *false negative* against an app that did open a menu, the fallback click will dismiss it and open another. CGWindowList detection was reliable in every app tested (2026-07-13), so this is judged the better trade than a silently dead hotkey — but it is the thing to check first if a menu ever flickers
